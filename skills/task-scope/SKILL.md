# 과제 범위

현업자의 목적·업무 맥락·성공 조건을 질문해야 할 때만 [질의응답 참조](references/stakeholder-elicitation.md)를 읽는다. 이미 자료나 기존 답으로 확인된 내용은 재질문하지 않는다.

1. 과제·자료·현재 구현을 읽고 확정 조건과 미확정 사항을 나눈다. 기존 답과 상태를 재사용한다.
2. 사용자·상황·문제와 입력에서 핵심 결과까지의 최소 흐름을 정한다. 사실·가정·임시 기준을 구분한다.
3. 구현 결정을 바꾸는 누락만 질문하고, 답을 기다리는 부분과 독립적으로 진행할 작업을 나눈다.
4. 관찰 가능한 수용 조건, 필수·선택·제외 범위를 정한다. 고정 코드·단발 모델 호출·에이전트 중 요구에 맞는 방식을 선택한다.
5. 범위가 정해지면 구현으로 넘어간다. 목적·제약·성공 조건이 바뀔 때만 해당 항목을 갱신하고 내부 구조 변경마다 기획을 다시 시작하지 않는다.

긴 작업만 기존 상태 기록에서 단계로 나눈다. 단계마다 목표·필수 결과·완료 조건·다음 행동을 정하고 검증할 사례가 있으면 ID를 연결한다. project·roadmap·phase의 같은 진행 상태를 별도 파일에 반복하지 않는다. 짧은 수정에는 단계 운영을 추가하지 않는다.

기존 과제 기록의 문제·흐름·조건·범위·불확실성만 갱신한다. 현재 소요시간을 모르면 미측정으로 남긴다. 수용 조건을 정의하는 것이 이 스킬의 종료점이다. 도구 단독 시험·최종 검증은 중복 수행하지 않으며 PRD 항목 수와 서식을 강제하지 않는다.
