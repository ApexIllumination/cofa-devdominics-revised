# 기술·구현 설명과 이해 확인

구현을 설명할 때는 화면에서 사용자가 한 행동과 그 직후 보이는 변화로 시작한다. 같은 장면을 따라가며 변화가 생긴 이유를 설명하고, 마지막 줄에 실제 코드 흐름을 한 줄로 정리한다. 화면이 없는 기능은 사용자가 본 입력·출력이나 오류에서 시작한다. 흐름에 쓰는 함수·상태·호출 순서는 소스로 확인하고, 확인할 수 없는 연결은 미확인으로 표시한다. 개념만 묻는 경우 실제 구현 경로를 만들어 붙이지 않는다.

“왜 필요한가”, “어떻게 돌아가는가”에는 사용자가 해 본 행동 하나에서 시작한다. 단순한 방식으로 어디까지 되는지 보여주고, 요구 하나가 바뀌면 어디서 막히는지 짚는다. 그때 필요한 개념에 이름을 붙이고 같은 사례로 돌아와 결과를 설명한다. 실제 구현을 묻는 경우 코드·데이터에서 확인된 경로만 따라간다. 짧은 사실 질문은 직접 답한다.

여러 계층을 연결하거나 낯선 개념을 풀어야 하면 [수업의 설명 구조와 적용 예](references/teaching-flow.md)를 참고한다. 일반 구현 설명은 코드 흐름 한 줄로 마친다. 아래 절차는 이해 점검을 요청했거나 합의했을 때 사용한다. AI 사용이 금지된 평가 단계의 제한은 두 경우 모두 적용한다.

## 구현 이해 확인

요청받은 연습 또는 합의한 작업 중 점검 시점에 적용한다. 평가의 후속 서술형 등 AI 사용이 금지된 단계에서는 문항을 읽거나 답안을 작성·수정하지 않는다. 현재 단계의 허용 범위는 해당 시험 지침을 따른다.

1. 실제 코드·데이터·실행 결과에서 입력→처리→결과, 중요한 선택의 당시 이유, 검증과 한계를 짚는다. 현업 답변으로 달라진 선택은 어떤 답변·자료 때문에 구현을 바꿨는지 연결한다. 모든 함수·라이브러리 내부를 암기하게 하지 않는다.
2. 사용자가 필요한 부분을 자신의 말로 설명하거나 변경 영향을 예측하도록 돕고 구현과 대조한다. 데이터 작업이면 단위·결측·식별자·집계 규칙 중 결과를 바꾸는 판단도 포함한다. 이미 확인했고 변경되지 않은 내용은 재질문하지 않는다.
3. 틀린 부분은 구체적 파일·작은 실행 예제로 보완한다. 설명이 부족하거나 답변이 없으면 이해 확인 대기로 남긴다.
4. 대기는 이해 확인에만 적용한다. 독립적인 구현·검증·제출 준비를 멈추지 않는다.

설명서 생성·읽기만으로 이해했다고 기록하거나 설계 이유를 사후에 지어내지 않는다. 질문은 현재 구현의 분기·제약·실패·변경 영향에서 뽑는다. 연습 지원과 실제 평가 답변을 구분하고 평가 중 도움은 해당 허용 범위를 따른다.

기존 과제 기록에 확인한 설명과 남은 이해 공백만 보완한다. 별도 모범 답안 파일이나 기능마다 반복하는 퀴즈를 필수로 만들지 않는다. 시간이 부족하면 설명할 핵심 판단을 좁히고 미확인을 사실대로 남긴다.
