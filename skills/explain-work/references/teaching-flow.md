# 문제에서 출발하는 설명

네 수업은 앞에서 해결한 일을 다음 질문의 출발점으로 삼는다. 방명록 글을 화면에 보여주는 데 성공하면, 이번에는 서버가 재시작돼도 그 글이 남는지 묻는다. 독자는 방금 이해한 예를 그대로 가지고 저장의 필요성을 생각할 수 있다.

| 수업과 전사 위치 | 사례가 이끄는 질문 | kit에서 가져올 설명 방식 |
|---|---|---|
| 1강 프론트엔드 · 03:54, 07:11 | 문서 한 장을 보여줄 수 있다. 여러 페이지의 모양을 함께 바꾸려면? 클릭한 부분만 바꾸려면? | 화면에서 바꾸려는 대상부터 짚는다. 공통 모양은 CSS로, 브라우저가 문서를 표현한 구조는 DOM으로 이름 붙인다. 사용자 행동 뒤 어떤 부분이 갱신되는지 돌아본다. |
| 2강 백엔드 · 00:39, 05:05 | A가 방명록에 쓴 글을 다음에 들어온 B도 읽으려면? 서버가 꺼졌다 켜져도 읽으려면? | 글 한 건을 입력한 순간부터 서버의 처리, 저장, 다음 조회까지 따라간다. 각 단계에서 누가 무엇을 받아 누구에게 넘기는지 밝힌다. |
| 3강 DB와 스토리지 · 04:47, 21:37~22:59 | 두 표로 나눈 정보를 다시 연결하려면? 프로필을 조회할 때 사진 파일은 어디서 가져오는가? | 식별자로 연결되는 기록과 파일의 역할을 같은 사용자 경험 안에서 구분한다. 사진을 바꾸면 객체와 DB의 참조 중 무엇이 바뀌는지 실제 저장 방식으로 설명한다. |

## 설명에 적용하기

사용자가 아는 출발점을 하나 고른다. SQL의 JOIN을 이미 이해한다면 문법부터 다시 가르치기보다 기준표의 키 하나가 두 번 나타날 때 실적 한 행이 몇 행으로 늘어나는지 보여준다. 비유가 필요하면 대응하는 역할을 짚고 실제 데이터로 돌아온다. 강의의 연대기나 도구 목록은 질문에 필요한 만큼 쓴다.

**예시 질문 — 평균 추가 통근시간이 15분 이내인데 왜 탈락인가요?**

두 사람이 자차보다 각각 0분, 20분 더 걸리면 평균은 10분입니다. 평균만 보면 두 번째 사람이 겪는 20분이 가려집니다. 이 예의 정책은 각 승객에게 15분까지 허용하므로 이 노선은 탈락합니다. 화면의 평균은 전체 부담을 비교하는 데 쓰고, 선택 가능 여부는 한 명이라도 상한을 넘었는지로 판단합니다.

위 숫자는 설명용이다. 실제 셔틀 예제를 설명할 때는 입력의 단위부터 확인한다. 승객을 집단으로 묶은 구현이라면 집단별 추가 시간과 인원수로 가중 평균을 구하는 과정을 보여준다. 사용자가 연습을 요청하면 두 번째 사람의 추가 시간이 정확히 15분으로 바뀔 때 이 제약의 판정이 어떻게 달라지는지 예측하게 한다.

## 화면 동작을 설명하는 예

이천의 두 번째 운영안을 비교함에 담으면 ‘나란히 비교’ 버튼이 나타납니다. 아직 버튼을 누르지 않아도 페이지 아래에는 두 안의 비용이 나란히 보입니다. 두 번째 안을 담는 순간 React가 선택한 두 ID로 운영안을 찾아 비교 영역을 그렸기 때문입니다. 목록에서 버튼을 누르면 브라우저가 그 영역까지 스크롤합니다.

**코드 흐름**　두 번째 안 선택 → `setSelected` → `selected.map(...)`으로 두 안 조회 → `comparison.length === 2`이면 비교 영역 렌더 → ‘나란히 비교’ 클릭 → `scrollIntoView()`.

## 정확성

자료는 자동 자막과 대조한 교정 전사본 네 편이며 음성 직접 청취 검수는 완료되지 않았다. 검수 메모의 미확정 발음·숫자·주소는 예시로 재사용하지 않는다. 강의에서 주제를 연결한 순서는 학습 순서다. 특정 기술이 반드시 그 역사적 이유 하나로 생겼다고 옮기지 않는다.

기술 설명은 검수 메모의 구분을 지킨다. 예를 들어 CSS의 캐스케이드와 상속을 구분하고, 서명된 JWT가 보장하는 무결성과 암호화가 제공하는 기밀성을 구분한다. DB와 파일 저장소를 나눠 쓰는 선택은 해당 서비스의 접근 패턴으로 설명한다. 배포 설명에서는 웹 서버와 앱 서버가 어디에 배치됐는지 실제 구성을 확인한다.
