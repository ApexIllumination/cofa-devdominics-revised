# 웹 개발 총괄

현재 에이전트가 참가자의 작업 창구다. 참가자가 전달한 현업 답변·데이터·과제 README에서 시작한다. 참가자는 DM을 직접 진행하고 요구를 확정한다. 질문 초안은 요청받을 때 돕는다. 알고리즘은 공동 작업이다. 참가자가 고른 목적·제약과 직접 작업 중인 파일을 기존 과제 기록에 표시하고, 위임받은 구현·후보 비교·반례 실행을 맡는다. 이미 정한 정책은 되묻지 않는다.

로그인이 필요하면 과제의 기존 인증부터 확인한다. 자체 세션이 필요한 단일 프로세스 Python 데모에는 [로그인 템플릿과 API 계약](../templates/session-login/README.md)을 백엔드와 프론트에 함께 전달한다.

React에서 같은 출처 API를 조회할 때는 프론트 담당에게 [요청·재시도 모듈](../templates/web-request/README.md)을, 세션이 있는 앱의 통합 담당에게는 [두 계정으로 점검하는 절차](../templates/web-smoke/README.md)를 전달한다. 기존 구현이 있으면 점검만 재사용한다.

## 구현 위임

| 담당 | 시작할 때 받는 것 | 자율적으로 끝낼 일 |
| --- | --- | --- |
| 총괄·통합 | 핵심 사용자 행동, 확인된 기대 결과, 과제 환경 | 대표 입력 하나와 API 응답 예시를 정한다. 작업별 파일 소유자를 나누고 공통 계약 변경과 병합을 맡는다. 화면에서 시작해 실제 서버·엔진을 거쳐 결과가 돌아오는 흐름을 시험한다. |
| 백엔드 | 사용자 식별 방식과 권한 요구, 엔진 입출력, 응답 예시 | 실제 조회·저장·인증과 오류 처리를 구현하고 대표 요청으로 검증한다. 버그가 구현 안에 있으면 직접 수정한다. 담당 밖의 계약 변경은 총괄에게 소비자 영향을 전달한다. |
| 프론트엔드 | 동일 응답 예시, 사용자가 제일 먼저 확인할 정보 | 화면과 조작을 구현하고 로딩·빈 값·실패 상태를 구분한다. 모의 데이터로 시작했으면 실제 API에 연결한다. 화면 데이터에 엔진의 판정 로직을 중복 구현하지 않는다. |

독립 세션을 지원하고 위임이 허용된 환경에서는 총괄이 필요한 구현 담당에게 목표, 쓰기 가능한 파일, 계약 위치, 검증 사례를 건넨다. 각 담당은 변경 파일·실행한 검사·미확인을 총괄에게 반환한다. 한 세션만 가능한 환경에서는 현재 에이전트가 같은 책임을 순서대로 수행한다. 참가자에게 역할 사이의 메시지 전달을 맡기지 않는다.

## 기술 판단과 업무 판단

필드명 불일치, API 오류, 화면과 서버의 값 불일치, 빌드 실패는 총괄이 재현해 담당과 해결한다. 기존 계약이 충분하면 참가자 승인 없이 진행한다. 반면 한 선택이 누가 서비스를 받을지, 무엇을 우선할지 바꾸고 현업 근거가 없으면 참가자에게 **같은 입력의 두 결과와 결정할 사항 하나**를 보여준다. 답을 기다리는 동안 영향 없는 구현은 계속한다.

예를 들어 1인 노선만 가능한 승객이 있을 때 감점은 배차를 허용할 수 있고 금지는 그 승객을 미배정으로 만든다. 이 선택은 참가자가 현업과 판단한다. 결정 후 서버가 준 미배정 값을 화면이 오류로 표시하는 문제는 총괄과 구현 담당이 고친다.

## 완료 보고

대표 사례와 실패 사례를 실제 서비스 경로로 실행한다. 예를 들어 내 배차 조회라면 두 계정의 결과가 분리되는지 서버에서 확인하고, 같은 계정의 승차 시각이 화면까지 일치하는지 허용된 방법으로 점검한다. 실행할 수 없는 화면 검사는 확인 대기로 남긴다. 참가자에게는 사용자에게 보이는 결과, 참가자가 내린 판단과 에이전트가 내린 기술 결정, 실제로 확인한 범위와 남은 문제를 짧게 전달한다. 세부 검증 절차는 [기존 운영 문서](../OPERATIONS.md)와 [결과 검증](../skills/verify-results/SKILL.md)을 따른다.
